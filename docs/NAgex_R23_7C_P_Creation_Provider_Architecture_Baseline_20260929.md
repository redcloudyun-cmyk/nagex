## 1. Executive Summary

NAgex R23.7C-P establishes the canonical provider architecture baseline for all multi-format creation capabilities (`DOCUMENT`, `IMAGE`, `PRESENTATION`, `VIDEO`). 

This architecture prevents future creation capabilities (e.g. `R23.7C-C Image`, `R23.7C-D Presentation`, `R23.7C-E Video`) from inventing siloed provider abstractions or hardcoding third-party vendor APIs into domain executors.

### Core Architectural Invariants
1. **ModelRouter vs CreationProviderRouter Separation:** `ModelRouter` selects reasoning/synthesis LLM models for text intelligence tasks. `CreationProviderRouter` selects specialized generation and rendering engines (`ImageProviderPort`, `PresentationProviderPort`, `VideoProviderPort`).
2. **Canonical Spec Ownership:** NAgex defines provider-neutral creation specifications (`ImageCreationSpec`, `PresentationCreationSpec`, `VideoCreationSpec`). Third-party DTOs never become NAgex domain specifications.
3. **Canonical Artifact Ownership:** NAgex mints and persists canonical artifact IDs (`doc_*`, `img_*`, `pres_*`, `vid_*`) and normalizes provider execution outputs into NAgex artifacts (`DocumentRecord`, `ImageRecord`, `PresentationRecord`, `VideoRecord`) with subordinate `ProviderExecutionMetadata`. Provider job IDs/URLs never masquerade as canonical artifact identities.
4. **Provider-Independent Revision Lineage:** Revisions reference parent NAgex artifact IDs (`parentArtifactId`, `revisionIndex`), enabling cross-provider revision lineage (e.g., Image v1 generated by Provider A, revised v2 by Provider B).
5. **Truthful Execution (`FAKE_SUCCESS_PATHS = 0`):** Provider failures, timeouts, unconfigured states, or empty outputs return `FAILED` or `UNAVAILABLE` states and never produce fake success artifacts.

## 4. ModelRouter vs CreationProviderRouter Separation

`ModelRouter` and `CreationProviderRouter` answer two fundamentally distinct architectural questions:

* **`ModelRouter` (`src/model-gateway/unified-model-router.ts`):** Answers *"Which language/reasoning LLM should perform this model reasoning task?"* (e.g., Gemini 1.5 Pro for 1M context analysis, Nebius Llama 3.3 70B for fast synthesis).
* **`CreationProviderRouter` (`src/creation/providers/creation-provider-router.ts`):** Answers *"Which specialized execution engine should render/generate this creation asset?"* (e.g., FLUX / Imagen 3 for images, Gamma / Canva / Native PPTX engine for presentation slide decks).

A complex creation workflow (e.g., presentation drafting) uses `ModelRouter` for slide narrative planning, and then uses `CreationProviderRouter` to route the slide deck spec to a presentation rendering provider port.

```typescript

  creationKind: CreationKind;
  purpose?: string;
  instructions?: string;
  locale: 'en' | 'ko';
  sourceRefs?: CreationSourceRef[];
  contextRefs?: CreationSourceRef[];
  userPreferences?: Record<string, unknown>;
  brandContext?: {
    brandName?: string;
    primaryColor?: string;

  };
  outputRequirements?: {
    format?: string;
    quality?: 'DRAFT' | 'BALANCED' | 'HIGH' | 'ULTRA';
  };
```

### Domain Specifications
* **`ImageCreationSpec`:** Defines `subject`, `composition`, `style`, `aspectRatio` ('1:1' | '16:9' | '9:16' | '4:3' | '3:2'), `referenceImages`, `textRequirements`, `outputUsage`, `qualityPreference`, and `constraints` (`negativePrompts`, `transparentBackground`).
* **`PresentationCreationSpec`:** Defines `title`, `audience`, `tone`, `slides` (`PresentationSlideSpec`: `slideId`, `objective`, `title`, `narrative`, `bullets`, `visualIntent`, `imagePrompt`, `chartSpec`, `sourceRefs`), `speakerNotes`, `references`.

## 6. Domain Capability & Availability Models

### Provider Availability States (`ProviderAvailabilityStatus`)
* **`UNCONFIGURED`:** Provider installed but credentials/endpoint unconfigured.
* **`CONFIGURED`:** API key/endpoint present, pending health check.
* **`AVAILABLE`:** Fully operational and capable of receiving creation specs.
* **`DEGRADED`:** Operating with elevated latency or partial capability limits.
* **`UNAVAILABLE`:** Outage, rate-limit exhaustion, or health check failure.

### Provider Capability Objects
Providers declare explicit capabilities (e.g., `ImageProviderCapabilities.transparentBackground`, `PresentationProviderCapabilities.exportPptx`, `VideoProviderCapabilities.maxDurationSeconds`) rather than inferring features from provider names.

## 7. Explainable Provider Routing Policy

`CreationProviderRouter` evaluates candidate provider ports and returns a `ProviderRoutingDecision<TPort>` containing explicit, explainable reason codes:

* **`EXPLICIT_PROVIDER`:** User or policy explicitly requested a provider; validated for configuration, availability, and capability.
* **`REQUIRED_CAPABILITY`:** Selected provider matching required spec capabilities (e.g., `transparentBackground`, `aspectRatio`).
* **`DEFAULT_PROVIDER`:** Selected primary available provider for the domain.
* **`PRIVACY_POLICY`:** Selected provider respecting local/private data boundary requirements.
* **`FORMAT_REQUIREMENT`:** Selected provider matching requested output format (e.g. PPTX export).
* **`PROVIDER_UNAVAILABLE_FALLBACK`:** Primary provider unavailable; routed to configured fallback.

If an explicit provider override fails capability checks or is `UNCONFIGURED`/`UNAVAILABLE`, `CreationProviderRouter` fails closed with `CAPABILITY_UNSUPPORTED` or `PROVIDER_UNAVAILABLE` rather than silently ignoring requirements.

## 8. Artifact Normalization & Revision Lineage

1. **Provider Metadata Subordination:** Provider execution returns `ProviderExecutionResult<TOutput>` with `ProviderExecutionMetadata` (`providerId`, `engineOrModel`, `providerJobId`, `providerAssetId`, `latencyMs`).
2. **Canonical Artifact Mints:** NAgex mints canonical IDs (`doc_*`, `img_*`, `pres_*`, `vid_*`) owned by NAgex. Provider job IDs are saved as subordinate metadata inside the canonical record.
3. **Provider-Independent Lineage:** Revisions reference parent NAgex artifact IDs (`parentArtifactId`, `revisionIndex`). Revisions can switch providers without breaking artifact lineage.

---

## 9. Security, Credentials & Privacy Boundaries

* **Credential Protection:** Provider API keys and secret tokens reside strictly server-side in configuration stores. No secret ever enters client responses, artifact records, execution metadata, telemetry, or activity logs.
* **Tenant & Owner Isolation:** Every canonical spec and store lookup enforces explicit `tenantId` and `ownerId` boundaries. Cross-tenant or unauthorized user access is denied (`404 / DENIED`).
* **Delimiters & Injection Safeguards:** Source context and external text references are enclosed in strict delimiters (`"""`) to protect against prompt injection.
