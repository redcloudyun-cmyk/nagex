# R23.6E Known Debt — GOOGLE_SCOPE_LEGACY_FIXTURE_DRIFT

**Status:** Pre-existing, unrelated to R23.6E. Not fixed as part of R23.6E.
**Scope affected:** `google` (test-scope registry)
**Failure count:** 24 of 455 tests
**Discovered:** during R23.6E Phase E validation (2026-09-27)

## Summary

Running the `google` test scope (`node scripts/nagex-test-scope.mjs google`)
produces 24 failures. These are **not caused by R23.6E** (Phases A–F).

## Evidence this is pre-existing

- Reproduced identically (same 24 test names, same failure) on the R23.6E
  Phase D commit, before any Phase E code existed — verified via `git stash`
  isolating all Phase E changes and re-running the scope.
- Reproduced identically again after Phase F — confirmed via a diff of the
  failing-test-name set (timing noise stripped) between the Phase-D-only run
  and the Phase-F-complete run: zero difference.
- Ruled out `NAGEX_TOKEN_ENCRYPTION_KEY` (a plausible, simpler explanation
  given the `google_oauth_persistence_disabled` warning every test run logs)
  by explicitly setting the variable for one run: identical 24 failures,
  same count, same names.

## Root cause (best evidence to date, not fully resolved)

The representative failure:

```
test: "no automatic write without approval: create-event is rejected before any approval exists"
  (tests/calendar_approval_ui.test.ts)
  Expected values to be strictly equal:
  + actual:   'GOOGLE_CALENDAR_DISCONNECTED'
  - expected: 'APPROVAL_NOT_FOUND'
```

This test constructs `GoogleCalendarService` with the older 6-argument
pattern (`tokenStore, approvals, audit, memory, fetchFn, getConfig`),
injecting a fully working `InMemoryGoogleOAuthTokenStore` with a valid saved
token, and a fixed non-null `getConfig()` fake — both of which should be
sufficient for the service to resolve a "connected" state.

Instead, the credential-broker layer added by R23.4V
(`GoogleCredentialAccessService`/`CredentialBrokerService`, now
auto-constructed inside `GoogleCalendarService`'s/`GmailService`'s
constructor whenever `credentialAccess` is not explicitly passed) appears to
never resolve a usable credential reference against these older fixtures,
so `withAccessToken` returns `null` and the pipeline reports
`GOOGLE_CALENDAR_DISCONNECTED` before the test ever reaches the
approval-flow assertion it actually intends to exercise.

The failing tests span several files that don't obviously share code
(`calendar_approval_ui`, `durable_task_runtime`, `capability_broker`,
`personal_home`/Home pooling, `task_approval_continuation`) — all of them
construct `GoogleCalendarService`/`GmailService` (directly or via a shared
harness) using this same older, pre-R23.4V constructor-argument pattern
without an explicitly injected `credentialAccess`. This is consistent with
one shared root cause (the credential-broker layer's interaction with the
older 6-argument constructor pattern) manifesting across every test file
that still uses it, rather than 24 independent bugs.

**This has not been fully root-caused to a single line of code** — only
narrowed to "R23.4V's credential-broker construction defaults do not
resolve a connected state for the pre-R23.4V constructor-argument test
fixture pattern." A dedicated investigation, separate from R23.6E, is
recommended.

## Why this was not fixed inside R23.6E

- None of the 24 failing tests, nor any file they exercise, are files
  R23.6E touches (`src/agents/*`, `src/app/create-nagex-application.ts`
  wiring, `tests/r23_6e_real_e2e_agent.test.ts`, `tests/route_inventory.test.ts`).
- Root-causing and fixing this properly means either updating every one of
  these older test fixtures to the current constructor signature, or
  changing `GoogleCredentialAccessService`'s construction defaults — both
  are real, separate engineering decisions with their own blast radius,
  outside R23.6E's explicit scope ("do not add new research, Gmail,
  approval, credential, workflow, or agent frameworks").
- R23.6E's own correctness for Gmail send/approval/credential handling is
  independently certified by 408 passing tests in the `r23-6e-real-e2e-agent`
  scope plus fully green `permission-approval-hardening` (147/147) and
  `credential-broker` (173/173) scopes — none of which exercise the older
  fixture pattern this debt is isolated to.

## Recommendation

A separate, dedicated pass should:
1. Confirm the exact point `GoogleCredentialAccessService.ensureReference`/
   `withAccessToken` fails to resolve a connected state for a directly-
   injected `GoogleOAuthTokenStore`.
2. Decide whether to update the 24 affected tests' fixtures to the current
   constructor pattern (passing an explicit `credentialAccess`), or adjust
   `GoogleCredentialAccessService`'s defaults to remain compatible with a
   directly-injected token store.

## R23.6E closure gate condition

Per the R23.6E Phase F directive: final certification checks the `google`
scope for **zero new failures**, not zero failures overall. This debt
(`GOOGLE_SCOPE_LEGACY_FIXTURE_DRIFT`, 24 known, pre-existing failures) does
not block R23.6E closure.
