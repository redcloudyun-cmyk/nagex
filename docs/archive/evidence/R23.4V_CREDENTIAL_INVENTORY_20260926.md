# R23.4V Credential Inventory — 2026-09-26

**Status:** SAFE TO IMPLEMENT WITH REQUIRED MIGRATION  
**Branch:** r23.4v-credential-broker  
**Baseline:** main after benchmark/directive merge

## 1. Existing credential/token stores

Canonical Google credential persistence currently lives in:

- src/integrations/google/token.store.ts
- src/integrations/google/token.crypto.ts

Primary types/implementations:

- GoogleOAuthTokenStore
- InMemoryGoogleOAuthTokenStore
- PersistentGoogleOAuthTokenStore
- googleTokenStore singleton

The persistent store writes one AES-256-GCM encrypted tenant→token map.

No second persistent Google token store was found in the inspected canonical composition path.

## 2. Current secret material

StoredGoogleToken contains:

- accessToken
- refreshToken
- expiresAt
- scope
- tokenType
- connectedAt

GoogleTokenResponse also carries accessToken and refreshToken.

The store's public getStatus() does not expose token values.

## 3. Encryption

src/integrations/google/token.crypto.ts uses AES-256-GCM.

NAGEX_TOKEN_ENCRYPTION_KEY accepts:

- 32-byte base64
- 64-character hex

Invalid/missing key returns null.

PersistentGoogleOAuthTokenStore currently falls back to in-memory-only behavior if the key is absent or invalid.

This is truthful in logs but does not satisfy the final R23.4V production invariant by itself.

Required R23.4V behavior:

- explicit CONFIGURED / DEGRADED / UNAVAILABLE classification
- persistent secret write must never fall back to plaintext
- dev/test ephemeral mode must be explicit

## 4. Critical identity gap: tenant-only token ownership

Current GoogleOAuthTokenStore methods are tenant-keyed only:

- save(tenantId, token)
- clear(tenantId)
- isConnected(tenantId)
- getStatus(tenantId)
- getValidAccessToken(tenantId, ...)
- revoke(tenantId, ...)

The map is tokensByTenant.

There is no principalId/user binding in the credential record or key.

This is incompatible with the R23.4V target invariant:

CREDENTIAL_USER_BOUND=1

Required migration:

tenantId + principalId + provider/account identity

must become the canonical credential ownership key.

Do not preserve tenant-only ownership as the final broker model.

## 5. OAuth callback identity gap

src/http/routes/google-oauth.routes.ts currently:

- reads tenant from x-nagex-tenant or default tenant
- uses one global pendingGoogleOAuthState string
- exchanges the authorization code
- saves via googleTokenStore.save(tenantId, token)
- audits the connect event with hardcoded actor usr_admin_001

This means the OAuth continuation does not currently bind the authorization flow to a principal.

Required R23.4V correction:

OAuth state must bind at least:

- tenantId
- principalId
- nonce/state id
- createdAt / expiry
- one-time consume

The callback must restore the same tenant/principal identity and write the credential under that identity.

A browser callback must not trust a new caller-supplied principal header as the source of truth for the original OAuth initiation.

## 6. Gmail / Calendar token resolution

GoogleCalendarService and GmailService share the same googleTokenStore.

The shared GoogleCapabilityExecutionPipeline resolves access tokens through the token store and passes the raw access token only into provider execution functions.

This is a good migration seam.

Target:

GoogleCapabilityExecutionPipeline
→ CredentialBroker.withCredential(...)
→ provider callback

The raw token may exist transiently inside the privileged provider callback, but must not be returned outward.

## 7. Refresh path

Expired tokens are transparently refreshed in getValidAccessToken().

refreshGoogleAccessToken() receives the raw refresh token and returns a refreshed GoogleTokenResponse.

Current behavior correctly preserves the existing refresh token when Google does not return a new one.

R23.4V must move this behavior behind the broker/store privileged boundary without exposing refresh tokens.

## 8. Disconnect / revoke

revoke() currently:

- reads raw access token internally
- best-effort revokes it with Google
- always clears local state

This is compatible with a broker design if moved behind owner-bound credential access.

## 9. Existing persistence tests

tests/google_oauth_persistence.test.ts already proves:

- restart persistence with encryption key
- access-token restore
- refresh-token restore
- automatic refresh persistence
- fail-closed corrupted file
- fail-closed wrong encryption key
- disconnect deletes persisted credentials
- status does not expose tokens
- ciphertext file does not contain token plaintext
- mode 0600 on POSIX
- refresh-token preservation
- atomic replacement

These tests should be retained and migrated, not replaced.

## 10. Current raw-secret exposure assessment

Observed raw secret paths are internal:

- OAuth token exchange result
- token store memory
- refresh call
- provider Authorization use
- revoke call

Observed public status path exposes only:

- configured
- connected
- scopes
- expiresAt

No intentional plaintext credential API was found in the inspected path.

However R23.4V still requires canary-secret propagation tests because absence of an explicit API does not prove the value cannot leak through logs/errors/activity/model context.

## 11. Canonical migration constraints

Required:

CREDENTIAL_SOURCE_OF_TRUTH_COUNT=1
PARALLEL_GOOGLE_TOKEN_SOURCE=0

The current token store should be migrated or adapted behind the new broker rather than duplicated.

Recommended migration model:

CredentialReference
→ tenantId
→ principalId
→ provider=GOOGLE
→ account/credential identity
→ scopes/status metadata
→ encrypted secret payload owned by privileged store

Google token persistence can remain the initial storage implementation while the access contract changes.

## 12. Permission relationship

R23.3T remains authoritative.

Credential availability never grants action permission.

Required sequence:

Agent proposal
→ PermissionDecisionService
→ Human Approval when required
→ CredentialBroker
→ provider execution

HAS_CREDENTIAL != MAY_EXECUTE
