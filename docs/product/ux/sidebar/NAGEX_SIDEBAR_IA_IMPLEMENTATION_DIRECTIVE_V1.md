# NAgex Sidebar IA Implementation Directive v1

## Task Name

`NAGEX-SIDEBAR-IA-FEATURE-MAPPING-AND-IMPLEMENTATION — ONE SHOT`

---

## MISSION

Refactor the NAgex left-sidebar information architecture and the functions behind it according to the canonical Sidebar IA v1.

The sidebar must become a stable user navigation model, not a list of internal AI/agent infrastructure.

Canonical top-level navigation:

```text
Home
Inbox
Create
Canvas
Tasks
Knowledge
Activity
Settings
```

Approval is NOT a primary top-level navigation destination.

Live approval/execution belongs in the Right Execution Rail.

Deferred/background approvals belong under:

```text
Inbox → Approvals
```

Do not merely rename labels.

Audit current features, map them to the canonical destinations, move/merge/remove duplicated UI, and wire the resulting navigation to real product functions.

---

# 1. FIRST: INVENTORY CURRENT SIDEBAR AND FEATURES

Before modifying UI, inspect the current implementation and produce an internal feature map.

Identify all current:

- sidebar entries
- mobile navigation entries
- home shortcuts
- approval links
- activity/history links
- creation capability links
- tasks/automation links
- knowledge/files links
- settings links

Also identify hidden/duplicate entry points.

Create a mapping:

```text
CURRENT FEATURE
→ CURRENT LOCATION
→ CANONICAL DESTINATION
→ ACTION
   KEEP / MOVE / MERGE / HIDE / REMOVE / DEVELOPER_ONLY
```

Do not delete functioning capabilities merely because their navigation location changes.

# 3. HOME

Home must remain the primary start surface.

Required:

- multimodal command composer
- Your Day
- Active Work
- contextual recommendations
- Right Execution Rail integration

Home must NOT become a capability dashboard full of internal engine choices.

Structured shortcuts may exist, but natural-language intent remains primary.

---

# 4. INBOX

Refactor Inbox into the NAgex attention center.

Required sections:

```text
Needs Attention
Approvals
Suggestions
Notifications
```

### Needs Attention

Examples:

- scheduling conflict
- reservation requires confirmation
- task blocked
- important user decision required

### Approvals

Move deferred/background approval review here.

Do not make users navigate here for an approval generated by the command they are currently viewing; current-context approvals stay in the Right Execution Rail.

### Suggestions

Examples:

- create schedule
- reply
- reserve
- set reminder
- follow-up action

### Notifications

Examples:

- task completed
- condition triggered
- task failed
- task waiting for user

---

# 5. REMOVE APPROVALS AS PRIMARY SIDEBAR ITEM

If current sidebar has:

```text
승인 요청
Approvals
```

remove it from primary navigation.

Preserve the functionality through:

```text
Right Execution Rail
+
Inbox → Approvals
```

Ensure no approval records or capabilities are lost.

Update tests and routes carefully.

Do not break direct approval URLs if they are still required for compatibility.

If necessary, legacy approval route may redirect to Inbox Approvals.

# 7. CANVAS

Canvas must mean artifact editing.

Audit current Canvas implementation.

Place here:

- open/edit existing artifact
- page/block/layer manipulation
- reorder
- duplicate
- rename
- Undo/Redo
- versioning
- document/slide/image workspaces as actually supported

Do NOT duplicate Create's "start a new task" function.

If Canvas is not yet fully wired for a capability, show truthful supported state.

---

# 8. TASKS

Map all task/automation capabilities into Tasks.

Required user sections:

```text
Today
Upcoming
Recurring
Conditional
Background
Completed
```

Map existing task types:

- ONE_TIME
- RECURRING
- CONDITIONAL
- BACKGROUND

into user-friendly presentation.

Do not expose scheduler internals.

Each item should show at minimum:

- human-readable task
- next run / trigger
- current state
- last result
- pause/resume/cancel where supported

```text

```

---

# 10. ACTIVITY

Keep Activity deliberately simple.

Default list item fields:

```text
timestamp
action
target/context
result/status
```

Do not show normal users:

- Tool
- Route
- command status internals
- raw approval state
- commandId
- MCP
- model
- planner/router
- execution primitive
- low-level audit buttons

Technical details remain accessible only in developer/audit surfaces where already supported.

---

# 11. SETTINGS

Consolidate settings under:

```text
Account
Devices
Connections
Permissions
AI & Personalization
Privacy & Security
Appearance
```

### Account
Google / Microsoft identity and explicit linking

### Devices
Desktop/mobile/connected nodes/trust

### Connections
Gmail / Calendar / Drive / Plugins

### Permissions
data/action/notification permission management

### AI & Personalization
language, user-facing preferences, proactive suggestions

### Privacy & Security
approval/security/data controls/audit access

### Appearance
theme/layout preferences

Do not expose raw secret/token/config values to normal UI.

---

# 12. RIGHT EXECUTION RAIL

Preserve and integrate the Home UX lifecycle:

```text
AWAITING_APPROVAL
→ WORKING
→ VERIFYING
→ COMPLETED / FAILED
```

Approval is a state in an execution thread.

It is not a navigation category.

One user intent should normally use one evolving action card.

Do not create separate cards for approval, command, and verification when they represent the same user intent.

---

# 13. FEATURE PLACEMENT RULE

Use this canonical decision rule:

```text
START WORK
→ Home / Create

NEEDS USER ATTENTION
→ Inbox

EDIT EXISTING ARTIFACT
→ Canvas

DO LATER / RECUR / CONDITIONAL / BACKGROUND
→ Tasks

MANAGE INFORMATION / CONTEXT
→ Knowledge

REVIEW PAST ACTION
→ Activity

MANAGE PRODUCT / ACCOUNT / DEVICE
→ Settings

LIVE APPROVAL / EXECUTION
→ Right Execution Rail
```

Use this when reviewing future features.

Desktop may show an expanded sidebar.

Mobile may show a drawer / compact navigation.

But menu meaning must not change.

Do not create separate conceptual IA for mobile.
